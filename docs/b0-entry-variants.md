## ① 按股数下单（已实现，但——实测为 no-op）

> ### ⚠️ 更正（2026-10-11 10:15，实盘实测后）
> **这一节原先的结论是错的。** 实盘第一笔立刻暴露：`限价 0.96、成交 0.92 → 拿到 5.217387 股`，
> 即 `4.80 ÷ 0.92` —— 说明交易所**始终按"花掉的 USDC"交割股数**。
>
> 读 SDK（`node_modules/@polymarket/clob-client-v2/dist/order-builder/helpers/`）确认：
> ```js
> // 市价端点 getMarketOrderRawAmounts(BUY): rawMakerAmt = amount(USDC); rawTakerAmt = amount / price
> // 限价端点 getOrderRawAmounts(BUY):       rawTakerAmt = size(股);   rawMakerAmt = size × price
> ```
> 两条路签出的是**同一张订单**：`(makerAmount = USDC, takerAmount = 股数)`。而运行器里
> `notional = 限价 × 5股`，所以 `createAndPostMarketOrder({amount: notional})` 与
> `createAndPostOrder({size: 5, price: 限价})` **代数上完全相同**。
>
> **⇒ `takerBuyByShares` 对下单规模没有任何影响；原表中"昨夜 39 笔 −$0.09 → +$1.88"的差异来自采样噪声，不是这个改动。**
> **⇒ 也推翻了我更早的说法"崩盘时亏 $2.75 而非 $4.80"** —— 美元敞口恒为 `5 × 限价`，与成交价落在哪里无关。
> **⇒ 结论：Polymarket 的 BUY 是"花多少钱"导向的，股数无法被钉住，尾部也无法靠下单方式缩小。**
>
> 代码保留该开关（`takerBuyByShares`）仅供 A/B 两个端点，日志与注释已改为如实描述。**默认建议 false。**
>
> 真正能压缩尾部的是 **绝对止损**（见 `docs/b0-stop-loss-050.md`）：止损 0.50 时，普通入场亏 ≈ −$2.3、
> 崩盘成交（8.73 股）亏 ≈ −$0.5，都远小于 −$4.75；**唯一挡不住的是跳空**。

### 实现

**根因**：`src/btc-5m-latency-scalp.ts` 的 BUY 走的是
`createAndPostMarketOrder({ amount })`，而 SDK 对 `amount` 的语义是
`BUY orders: $$$ Amount to buy`（`node_modules/@polymarket/clob-client-v2/dist/types/ordersV1.d.ts`）。
交易所按 `amount / fill_price` 交割股数 ⇒ **成交价越低买到越多股**。

**改法**：新增配置 `takerBuyByShares`（env `<PREFIX>_TAKER_BUY_BY_SHARES`），
开启后 BUY 改走限价端点 `createAndPostOrder({ size })` + `OrderType.FAK`：

```ts
const shareSizedBuy = isTaker && side === "BUY" && this.cfg.takerBuyByShares;
const response = shareSizedBuy
    ? await this.client.createAndPostOrder(userOrder, options, this.cfg.orderType as unknown as OrderType.GTC | OrderType.GTD)
    : isTaker ? /* 原来的市价端点 */ : /* 原来的限价端点 */;
```

撤单兜底已存在（reconciler 的 `partial fill; cancel remainder`），记账走真实 trades API
（`summary.notional`），所以两种口径下 `entry_cost` 都正确。

### 实测：限价端点确实接受 FAK + 指定股数

`scripts/fak-limit-probe.ts` 挂一张距盘口 ≥10 分的 5 股 FAK 买单并立即查询：

```
post response: {"error":"no orders found to match with FAK order. FAK orders are partially filled or killed if no match is found.","orderID":"0xcaa7...","status":400}
getOrder @+1500ms: null                       ← 没有挂单滞留
cancel: "order can't be found - already canceled or matched"
VERDICT: FAK+size ACCEPTED and KILLED on arrival — safe for share sizing
```

**结论：安全。** FAK + 指定股数被接受，未成交时在到达即被 kill，不会留残余挂单。

## ② 等 N 秒再挂单

**建模**：信号 tick `t` 出现后等 `W` 秒，在 `t+W` 的采样点检查 `ask`，仍 ≤ cap 才下单、按该 ask 成交。

**成交率影响（你问的那个）**：

| 口径 | 成交率 |
|---|---|
| 等 0s（现状） | **63.6%** |
| **等 3s** | **59.3%（只降 4.3 pp）** |
| 等 5s | 47.5% |
| 等 8s | 45.6% |
| **等 3s 且要求 ask 仍 ≥0.95**（真正避开击穿） | **38.4%（降 25.2 pp）** |

**EV（44.9 天，按金额）**：

| 配置 | 成交 | 胜率 | 均价 | 总PnL | 回撤 |
|---|---|---|---|---|---|
| 等0s · 允许崩盘成交 | 5,805 | 94.50% | 0.9420 | **−$8.17** | 121.56 |
| 等3s · 允许崩盘成交 | 5,406 | 94.30% | 0.9401 | −$17.48 | 141.02 |
| 等5s · 允许崩盘成交 | 4,337 | 93.87% | 0.9327 | +$49.17 | 90.98 |
| 等0s · 要求存活 | 3,967 | 95.61% | 0.9546 | −$30.13 | 84.61 |
| **等3s · 要求存活** | **3,499** | **95.77%** | 0.9550 | −$5.21 | **55.69** |
| 等5s · 要求存活 | 2,462 | 96.02% | 0.9556 | +$20.42 | 42.95 |

**读法（三条）**：

1. **"等 3s"本身几乎不损失成交率**（−4.3pp）——因为大多数窗口 3 秒后价格还在带内。
2. **但它也不改善 EV**（−$17.5 vs −$8.2，**t=−0.20，噪声**）。等 5s/8s 那几格显示正收益，但每笔 t 值都 <1，且同一配置在 lag 1s/2s 之间能差 $25（+$45.47 vs +$20.42）——**全是噪声**。
3. **"要求信号存活"确实消除了击穿**：胜率 94.50% → 95.77%，回撤 121.6 → 55.7（腰斩以上）。**但 EV 反而更差**——因为它把「崩盘便宜成交」整批剔掉了，而那批净 +$22（见 `b0-loss-postmortem.md` §5.3）。

> **所以：你的机制判断是对的（3s 后假报价消失），但结论相反。** 击穿后的便宜成交大多是"噪声回撤"，会弹回来；剔掉它们等于剔掉利润。
> **唯一值得用的是它的风控属性**：回撤减半。如果你更在意回撤而不是 EV，`等3s + 要求存活` 是合理配置。

## ③ margin ≥ 1bps 门槛（"开盘价附近不许进场"）

**建模**：在 entry tick 上要求方向性 `fav_margin ≥ X` bps。

**累积门槛效果**（44.9 天，n=5,805）：

| 门槛 | 保留 | 胜率 | 总PnL |
|---|---|---|---|
| 无门槛 | 5,805 | 94.50% | −$8.17 |
| ≥ 0 | 5,683 (97.9%) | 94.56% | −$15.41 |
| **≥ 1** | **5,225 (90.0%)** | 94.51% | **−$48.35** |
| ≥ 1.5 | 4,987 (85.9%) | 94.57% | −$39.55 |
| ≥ 2 | 4,734 (81.6%) | 94.68% | −$17.79 |
| ≥ 3 | 4,183 (72.1%) | 94.60% | −$57.53 |
| ≥ 5 | 3,035 (52.3%) | 94.96% | −$1.73 |
| ≥ 10 | 1,175 (20.2%) | 95.32% | +$14.49 |

**没有任何一个门槛（除 10，那是旧的 final-30-managed 配置、只剩 20% 交易）能改善结果，≥1 反而最差。**

**分档明细**（这是根因）：

| margin 档 (bps) | n | 胜率 | 95%CI | 总PnL | 均/笔 |
|---|---|---|---|---|---|
| < 0 | 122 | 91.80% | [86.9, 96.7] | +7.25 | +0.0594 |
| **[0, 0.5)** | 154 | 94.16% | [90.5, 97.9] | +1.99 | +0.0129 |
| **[0.5, 1)** | 222 | **96.40%** | [93.9, 98.8] | **+25.66** | **+0.1156** |
| [1, 1.5) | 238 | 93.28% | [90.1, 96.5] | −8.80 | −0.0370 |
| [1.5, 2) | 253 | 92.49% | [89.2, 95.7] | −21.76 | −0.0860 |
| [2, 3) | 551 | 95.28% | [93.5, 97.1] | +39.73 | +0.0721 |
| [3, 5) | 1,148 | 93.64% | [92.2, 95.1] | −55.80 | −0.0486 |
| [5, 10) | 1,860 | 94.73% | [93.7, 95.7] | −16.22 | −0.0087 |
| ≥ 10 | 1,175 | 95.32% | [94.1, 96.5] | +14.49 | +0.0123 |

**关键点：分档完全没有单调关系**（0.5–1 最好 +0.116、1.5–2 最差 −0.086、2–3 又好回来）。各档 95%CI 大幅重叠。
把 `[0,1)` 与 `[1,2)` 对撞：95.20%（n=458）vs 92.87%（n=491），差 2.33pp，**z=1.52，不显著**。

> **结论：数据不支持这个条件。** 「开盘价附近转悠」的那一组（0–1 bps，n=458）合计 **+$32.93**，
> 是收益最好的区间之一；加 1bps 门槛恰好把它切掉、留下更差的 [1,2) 组。
> 昨夜亏损 B 的 margin 是 +0.56bps——它落在**最好**的那个档里，纯粹是那 3.6% 的尾巴。

## 推荐组合

| 项 | 建议 |
|---|---|
| 按股数下单 | ✅ **开启**（`BUYSHARES=true`，已默认）—— 尾部风控 |
| 限价上限 | ✅ **0.95**（见 `b0-loss-postmortem.md` §5）—— 唯一有 EV 支持的改动 |
| 等 N 秒 | ❌ 不开；**若你更在意回撤**，可用「等 3s + 要求存活」（回撤 121.6 → 55.7，代价是 EV） |
| margin 门槛 | ❌ 不开 |

### 边界

1. **一切 EV 差异都在噪声内**：所有每笔 t 值 |t| < 1，所有 95%CI 含 0。$50 量级的差异由 ~320 次 −$4.8 的二元亏损主导。
2. **回测模型假设顶档 ask 有无限深度**，实盘出现过 `taker_no_match`（顶档太薄）。
3. **按股数下单把成交金额从恒定 $4.80 变成 5×成交价（$2.75~$4.80）**，
   若成交价偏低，单笔占用资金会少于 `minUsdcBalance` 门槛（$4.80）的假设——不影响正确性，但余额门槛可略放宽。
